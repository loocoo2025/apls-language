## 6. 正式 Finding

### C04-GOV-001-F001 — 独立 Session 请求无法表达全部独立授权动作

```text
SEVERITY: S1 — 重大（Major）
STATUS: OPEN
CATEGORY: GOVERNANCE / AUTHORIZATION
```

证据：

- `ROLE_INTERACTION_EXECUTION_POLICY.md:207-215` 规定，独立 Session 创建、正式 C04 Dispatch 和真实 Model 调用是彼此独立的 Action Class。
- `GOVERNANCE_EXECUTION_CONTRACTS.yaml:151-165` 分别列出这三类动作，并设置 `implication_between_action_classes: false`。
- `AI_CONVERSATION_ORCHESTRATION_RULES.md:1720` 明确要求三类动作分别具备适用授权。
- 但是，`AI_CONVERSATION_ORCHESTRATION_RULES.md:1683-1689` 中的规范性 `NEW_INDEPENDENT_SESSION_REQUEST` 写为：

```text
contract_refs:
- INDEPENDENT_SESSION_CREATION
- FORMAL_C04_DISPATCH_OR_REAL_MODEL_INVOCATION

required_action_classes:
- INDEPENDENT_SESSION_CREATION
- FORMAL_C04_DISPATCH | REAL_MODEL_INVOCATION | NOT_APPLICABLE
```

第二个槽位为互斥选择，因此，当一个正式 C04 请求同时创建 Session、发起正式 C04 Dispatch 并调用真实 Model 时，无法同时表达所需的三项独立授权。

违反依据 / 验收影响：

- 违反 CR-GOV-001 对独立 Action Class 的要求。
- 与该请求 Template 自身的机械规则矛盾。
- 符合现有结构的 Runtime 只能遗漏一项授权，或者自行发明合同外扩展，导致正式 Dispatch 或真实/付费 Model 调用可能缺少规定的独立授权。
- 这可能造成授权错误或 Gate 错误。

关闭条件：

1. 使 `INDEPENDENT_SESSION_CREATION`、`FORMAL_C04_DISPATCH` 和 `REAL_MODEL_INVOCATION` 在 `contract_refs` 与 `required_action_classes` 中都能被独立表达。
2. 为“只创建但不 Dispatch”“不产生新的真实 Model 调用但执行 Dispatch”以及“三类动作全部执行”的请求定义精确适用规则。
3. 确保任何适用 Action Class 缺少自身有效授权时，Schema 校验会拒绝正式 C04 操作。
4. 同步实例化该请求的外部 AI 配置和升级协议。
5. 形成新的不可变 Review Target。

默认路由：

```text
C00
→ Expert Escalation
→ Primary Executor 受控整改
→ 新精确 Commit
→ 新独立 C04 Session
```

需要负责人裁决：`NO`，前提是整改保持已经批准的独立动作语义不变。

### C04-GOV-001-F002 — 机器可读 Dynamic Role Profile 缺少必要的 Gate 与事实 Owner 绑定

```text
SEVERITY: S1 — 重大（Major）
STATUS: OPEN
CATEGORY: GOVERNANCE / CONTRACT / CURRENT_TRUTH
```

证据：

- `ROLE_INTERACTION_EXECUTION_POLICY.md:74-93` 要求每个受控 Session 的 Profile 与当前项目、Role、Task、Gate 和授权相匹配。
- Profile 最小内容明确包括“输入、输出和适用事实 Owner”。
- `GOVERNANCE_EXECUTION_CONTRACTS.yaml:22-50` 定义了机器必需的 Profile 字段，但既没有适用事实 Owner 字段，也没有明确的当前 Gate/Gate 绑定字段。
- `authorized_until` 是授权终点，不能唯一确定当前 Gate 或适用事实 Owner。

违反依据 / 验收影响：

- 机器合同被声明为权威字段目录，但它无法表达两项强制策略绑定。
- `TOOL_ENFORCED` 实现可以在没有证明 One Fact One Owner 分配、也没有证明与当前 Gate 兼容的情况下声明 `ROLE_PROFILE_READY`。
- 这会破坏 `PROCEDURAL_FALLBACK` 与 `TOOL_ENFORCED` 应保持等价的承诺，并可能导致以错误的事实 Owner 身份写入，或者在错误的 Gate 执行。

关闭条件：

1. 增加适用事实 Owner 和当前/适用 Gate 绑定所需的机器字段，或者定义同等明确、无歧义的结构化映射。
2. 明确这些字段如何与 Current Truth、Role Brief、Task 和 Authorization 进行校验。
3. 确保任一绑定缺失、过期或冲突时，`ROLE_PROFILE_READY` 都失败关闭。
4. 按适用范围同步 Profile 示例、启动指南和迁移映射。
5. 形成新的不可变 Review Target。

默认路由：

```text
C00
→ Expert Escalation
→ Primary Executor 受控整改
→ 新精确 Commit
→ 新独立 C04 Session
```

需要负责人裁决：`NO`，前提是不改变已经批准的事实所有权和 Gate 语义。
