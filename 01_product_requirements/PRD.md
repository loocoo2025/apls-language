## 1. 产品目标

### 一句话目标

提供一门以受控自然语言为唯一公开表面语法、面向人类和 AI Agent 的声明式软件系统规格语言，以及把规格转换为唯一、确定、可验证 Canonical IR 的编译器式工具链。

### 核心价值

人类用受控自然语言表达系统意图、运行结构、约束和验收条件；工具链负责拒绝歧义、验证一致性并向 AI Agent 提供稳定的 Canonical IR。用户默认不需学习或查看内部 DSL、AST 或 IR；只在主动请求检查或调试时展示。

### 首要成功标准

> 同一份合法 APLS 输入必须得到唯一的规范化解释；任何无法唯一解释的输入必须被拒绝，并返回稳定、可定位的诊断，禁止由 AI 静默猜测。

## 2. 目标用户

| 用户 | 目标 | 当前痛点 |
|---|---|---|
| 软件/系统架构师 | 把系统意图和约束交给 AI | 自然语言需求歧义大、难验证 |
| AI Coding Agent | 获得稳定的系统模型 | 仅凭代码和聊天难以理解全局语义 |
| 开发与验证工程师 | 检查实现是否符合规格 | 需求、设计、代码和测试缺少共同中间表示 |
| 工具开发者 | 构建 Parser、Checker 和后端 | 缺少稳定语法、类型和 IR 契约 |

## 3. 产品边界

### APLS 0.1 包含

- 正式词法与语法；
- 名称、类型、单位和引用规则；
- Execution Unit、Event、Channel、State Machine；
- Rule、Constraint、Safety、Acceptance；
- 解析、名称解析、类型检查和语义检查；
- Canonical IR；
- 稳定诊断代码与源码位置；
- 面向 Agent 的结构化输出；
- 最小一致性测试套件。

### APLS 0.1 不包含

- 替代 C、Rust、Python 的通用算法语言；
- 自动生成完整生产系统；
- 遗留代码自动逆向恢复；
- 多智能体自治编排；
- 在线自我修改或自主发布；
- 完整形式化证明器；
- 多个生产级目标后端。

## 4. P0 产品需求

### PRD-001 — 最终规范语义唯一

- Parser 可以为同一 Source 保留多个词法切分、Parse Tree 或其他中间分析候选。
- 所有仍有效候选经过名称/语义绑定、类型与单位检查及规范化后，必须收敛为恰好一个结构和语义等价的 `Canonical Frame` 等价类。
- 中间候选多解不得单独导致拒绝；不得通过任意优先级、最高概率、LLM 猜测或选择第一个 Parse 制造唯一性。
- 验收：同一输入的全部有效分析候选被完整、确定地处理；最终 Canonical Frame 等价类基数为 1，且重复执行得到结构相同的 Canonical Frame。

### PRD-002 — 拒绝歧义

- 如果输入存在多个合法解释，工具链必须拒绝输入。
- 不允许“选择最可能含义”、静默补全或自动改写后继续编译。
- “多个合法解释”规范定义为：语义绑定、检查与规范化后仍存在两个或以上不等价 Canonical Frame；零个有效 Canonical Frame 属于非法输入，不属于歧义。
- 验收：每个最终语义多解样例均返回非零结果、`AMBIGUOUS` 稳定诊断代码、精确源码范围和至少两个分歧见证；仅中间分析多候选但最终收敛的样例必须成功。

### PRD-003 — 确定的 Canonical IR

- 通过检查的程序必须生成唯一的规范化 IR。
- 与语义无关的空白、注释和允许的表面表示差异不得改变规范化语义。
- 验收：语义等价输入生成字节级稳定或经规范化比较相等的 IR。

### PRD-004 — 完整名称与类型检查

- 所有跨节点引用必须显式解析。
- 未定义名称、重复定义、类型不匹配、单位不匹配和非法循环依赖必须被诊断。
- 验收：负向样例不能进入 IR 生成阶段。

### PRD-005 — 语义冲突检测

- 状态转换、规则优先级、通信契约和约束之间的冲突必须有明确定义。
- 尚未定义冲突解决规则时，必须拒绝而不是选择任意结果。
- 验收：状态转换冲突和规则冲突均有稳定诊断。

### PRD-006 — 可操作诊断

- 每条错误至少包含诊断代码、严重度、文件、起止位置和原因。
- 可修复建议只能作为建议，不能在未授权时修改源文件。
- 验收：所有 Conformance 负向样例都能定位到最小相关源码范围。

### PRD-007 — Agent 安全消费

- Agent 默认消费已验证的 Canonical IR，而不是自行解释未经验证的源文本。
- 输出必须显式区分规范事实、说明文本、未知项和未决问题。
- 验收：IR Schema 能机械区分 normative、informative、unknown 和 open。

### PRD-008 — 编译器式最小工作流

工具链至少支持以下逻辑能力，具体 CLI 名称在架构阶段决定：

- Parse：源文件到 AST；
- Check：名称、类型与语义检查；
- Emit IR：输出 Canonical IR；
- Diagnose：机器可读与人可读诊断。

### PRD-009 — 受控自然语言公开界面

- APLS 唯一公开规范性 Source 必须是版本化的受控自然语言；
- APLS 0.1 首个规范性语言 Profile 是简体中文单语 Profile；其他语言以后使用独立版本化 Profile；
- 允许多个已批准等价句式映射为同一形式语义；
- 任一句子如果存在零个或多个完整语义必须拒绝，不得由 AI 猜测；
- 术语、同义表达、指代、数量、单位、模态、否定与时间范围必须由语言 Profile 机械定义；
- 用户无需查看花括号 DSL、AST 或 Canonical IR 即可完成正常编写、检查和修正流程；
- AI 可在编译事务外解释诊断和建议改写，但不能替编译器确定规范含义。

验收：每个合法句子最终产生恰好一个 Canonical Frame 等价类；多种中间 Tokenization/Parse 可收敛为同一规范含义；同义句组产生同一 Canonical Meaning；模糊量、未定义术语、多指代和最终作用域多解样例全部失败关闭。

## 5. P1 产品需求

- 从 Canonical IR 生成 Execution、Communication 和 State Graph；
- 从 Acceptance 生成测试骨架；
- 输出变更影响分析所需的稳定节点 ID；
- 支持一个受控参考案例验证端到端流程。

## 6. 非功能要求

- 确定性：输出不依赖随机数、模型温度或执行顺序；
- 可复现：相同工具版本和输入产生相同规范化结果；
- 可演进：语言与 IR 都具有显式版本；
- 可诊断：失败关闭，不产生部分可信结果；
- 可移植：核心语义不绑定特定 LLM 或实现语言；
- 可测试：每条规范性规则必须能映射到正向或负向一致性样例。

## 7. 关键约束

- 未被 CNL Grammar 接受的自由自然语言只能承担说明语义，不能隐式改变规范性语义；
- 任何默认值都必须在语言规范中显式定义；
- 实现不得用 LLM 推理替代 Parser、类型检查器或语义验证器；
- AI 可以提出修复建议，但重新编译必须基于用户或受控流程确认后的新输入；
- 研究文档当前状态均为 `REFERENCE`，除非其内容被提炼、质询并进入受控需求或决策。
